# 抓取延迟修复版

从 GRASP_HANDBOOK.md 提取源码并修改。此包尚未连接真机验证。

## 使用

把本包 robot_exec.py 和 tools/ 下全部文件覆盖到实际运行的 vision-rescue 对应位置。
尤其不要漏掉新增 tools/grasp_client.py。其他配套源码保留作参考。
原项目的 SDK、numpy、opencv、SSH 环境仍然需要。

现场有人看护并确认工作空间后，使用原来的抓取入口，例如：

    cd vision-rescue
    python3 tools/oneshot_grasp.py

此命令会实际移动机械臂和开合夹爪。底盘入口 drive_and_grasp.py 还会移动底盘。
观察台不能与抓取进程同时占用深度相机。本包未包含观察台 robot_web.py；start.command 是手册原样提取文件，不属于本次修复入口。

## 修改

- 一次抓取流程内复用同一个 SDK 进程，保留原有一次初始化方案。每次重新启动脚本仍有一次初始化成本。
- 三个抓取入口复用 grasp_client.py。按请求 id 匹配响应，跳过 SDK 日志；启动等待最多 30 秒，普通响应最多 40 秒。
- 夹爪统一非阻塞下发。每约 100ms 轮询状态，连续三次停止且宽度稳定后才判定，最多等 10 秒。
- 用“宽度高于指令值 3mm + effort 绝对值超过 15 + 连续状态稳定”识别接触，去掉原来 24mm 固定宽度门槛。约 22mm 的方块不会再被旧门槛排除。
- 接触仅表示存在阻挡，仍可能是桌面接触；不能单凭 effort 保证抓住方块。阈值沿用原项目 SDK 读数，未核实其物理单位，需现场标定，不提高夹持力度。
- 运动状态必须为 SUCCESS，笛卡尔终点误差须不超过 10mm；失败即中止后续动作。
- 执行端拒绝单关节变化超过 45 度的指令；此限制不能替代碰撞检查。
- plan_grasp 先高空对准再下降；drive_and_grasp 复核未对准就中止。
- 正常退出销毁 SDK 实例，不关整机、不自动张开夹爪；初始化异常不再二次 init。

## 超时后的含义

通信超时会使客户端连接失效并停止发送后续命令，但不能保证机器人上已经下发的动作立即停止。
现场应检查机器人实际状态，必要时使用硬件急停；不要直接重复启动抓取。
原执行通路仍为关节目标运动，没有可用碰撞规划；高空路点和增量限制不保证整个轨迹安全。

## 离线验证

    python3 -m unittest discover -s tests -v

8 个模拟测试通过：22mm 方块、空夹、张开到位、运动中状态、瞬时接触、日志与 id 匹配、读取超时、运动失败阻止后续发送及轮询稳定夹持。所有 Python 文件通过语法编译。
